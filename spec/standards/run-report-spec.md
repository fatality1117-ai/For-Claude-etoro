# 執行回報規格 v2

**每一趟自動化排程結束，一定要吐一份報告，格式固定，一字不差。**
產出者是 M9，去處是 `state/run-log.md`（append，最新在上）。

## 為什麼

排程沒跑，跟排程跑了但沒事做，在外觀上完全一樣。
2026-08-28 整天沒有貼文，沒有人發現，直到 Ed 隔天早上自己問。

- **空手也要發報告。** 什麼都沒做就報「跑了，沒事做，原因是 X」。
- **沒有報告 = 排程沒跑。** 這是唯一的判斷依據。
- 報告是最後一個動作，前面全部失敗也要報。
- Claude app 裡**只保留排程任務各自的對話串**當報告視窗，
  每一趟疊在裡面；同時 append 進 `run-log.md`，對話串會被捲掉。

## 輪替（2026-08-31 新增，`standards/requirements.md` 第六條）

`run-log.md` 只 append，而 Projects 沒有 patch API —— **每一趟 M9 都要整檔重寫才能加一筆。**
成本隨趟次線性成長，而且每次逐字複製都是一次截斷或竄改的機會。

- **`run-log.md` 只保留最近 12 筆回報**（工作記憶，漏跑偵測只需要這些）。
  溢出的逐字 append 進當月的 `archive/run-log-YYYY-MM.md`。
- **每月 1 日的生產趟做月結（2026-08-31 Ed 指定）：把上個月那份逐字檔清洗成一份摘要，
  覆蓋同一個檔名，逐字內容丟棄。** 檔案數量因此每月只增加一份，且大小固定。
  月結摘要只有六段，**其餘一律不留**：
  1. 趟數、收斂率、觸發抖動的最小／中位／最大值
  2. 當月發布清單只寫「共 N 篇，明細見 `state/published-index.json`」**（不重複那份資料）**
  3. 缺陷開關帳：當月新增幾筆、修掉幾筆、升級成改規格幾次，逐筆一行
  4. 規格變更清單：改了哪個檔、改了什麼、為什麼
  5. 預測校準：「我的預期」命中幾次、錯幾次、錯在哪個方向
  6. 三條教訓，寫成往後可以照做的規則，不是感想
- **`defects.json` 裡 `status` 為 `fixed` 的條目，只留 `id`、`level`、`detectedAt`、
  `resolvedAt`、一行 `detail`、一行 `fix` 摘要。** 長篇的修法與證據搬進
  `archive/post-review-log.md` 並在 `fix` 裡寫明搬到哪裡。
  open 與 needs-ed 的條目保持完整。
- 兩件事都由**生產趟**的 M9 做，出刊趟不做結構性搬移（出刊趟該是最便宜的一種）。
  超過 12 筆就在下一趟生產趟輪替，不必等特定日期。

## 「呼叫」的口徑（2026-08-31 07:18 定義）

**呼叫 = 對外部系統的工具呼叫。** 計入：eToro MCP、web_search / WebFetch、
`list_triggers` 等排程 API、`bash`。
**不計入：`project_read` / `project_write`。**

理由：規格與狀態檔的存取次數由文件結構決定，不是本趟的成本決策；
而各處既有的預算數字明顯都是按外部呼叫訂的
（`modules/README.md` §5 給 M0 的預算是 0-1，但 M0 光是規格動作就要讀
`run-log.md`、`defects.json`、`queue.json`；`flow/pipeline.md` §3 說出刊趟 3-5 呼叫，
同理）。若把 project 檔存取計入，出刊趟的 5 或 8 呼叫上限結構性不可能達成，
預算這個指標就失去意義。

**起因：** 同一週的回報用了兩種口徑 —— 出刊趟報「2 / 預算 5」（不含 project 檔），
2026-08-31 04:30 生產趟報「M0 10 呼叫」（含 project 檔）。
兩種數字放在同一份 `run-log.md` 裡無法互相比較。往後一律用本節定義。

## 發布通報（2026-08-31 Ed 指定，最優先）

**只要這一趟真的發布了貼文，報告的最前面就要有這個區塊，在「趟次」那一行之前。**
Ed 要的是「發完主動通報」，不是讓他自己去翻報告中段找產出。

```
════ 已發布 ════
[TYPE] <標題>
連結   <貼文網址；沒有網址就寫 postId>
時間   <台北 HH:MM>    HTTP <碼>
圖片   <伺服器回傳的尺寸>    Cashtag <解析 M / 草稿 N>    字元 <數>
複查   <逐字比對通過 / 發現什麼並當場 PUT 修正了什麼>
════════════
```

- 一趟發多篇就疊多個區塊，最新的在上。
- **沒有發布動作就不要放這個區塊**（空手趟用短報，見下）。
- 連結取 `POST` 或 `GET /api/v1/posts/{postId}` 回應裡真的有的欄位，
  **沒有就寫 postId，不准自己拼一個網址**。
- 這個區塊之外，下面的完整報告照常寫，一段都不能省。

## 短報格式（空手趟用，2026-08-31 新增）

**沒有發布、沒有降級、沒有新缺陷的趟次用短報。** 八成的趟次是這一種。
其餘一律用上面的全報。

```
════ 執行回報（短）════
趟次：<類型>   排程項 #<n>
日期：<TZ=Asia/Taipei date 的原樣輸出>
觸發：排定 <slot> / 實際 <台北時分> / 抖動 <分鐘>
結果：完成（<一句：為什麼空手，以及那是不是預期>）
呼叫：<實際> / 預算 <上限>
模組：叫用 <M0 M7 M9>；其餘未叫用。全部 OK，備援階 1。
      <有任何一個不是 OK 就不能用短報，改用全報>
規範：日期實測 [v]　不寫稿 [v]　空手仍回報 [v]　未寫他人 state 檔 [v]
缺陷：新增 <無>　修復 <無>　仍未解 <id 與已 open 趟數，一行>
漏跑：<有/無；本趟觀測到的 last_run 一行>
預期：<下一趟預期會怎樣，一句>
════════════════
```

**短報不是省略檢查，是省略排版。** 十五項檢查照跑，
只是全部通過時不必逐項列出來。任何一項沒過就自動升級成全報。

## 紀律

1. **模組健康表不准省略任何一列。** 沒跑的標「未叫用」。
2. **降級與跳過一定要寫原因。** 悄悄出一篇短稿等於把問題藏起來。
3. **缺陷修復要寫修法。** 只寫「已修」等於沒記錄。
4. **「需要 Ed 決定」只放需求層級的分歧。** 技術路徑是我的職權，
   自己選、自己修，修完在缺陷段報結果。見 `standards/authority.md` 第二部分。
5. **不要長篇解釋技術困難。** 一行講完是什麼、修了沒有。
6. **「我的預期」不准省略。** 預期錯了比沒預期更有價值，那是校準訊號。
7. **呼叫數一律用上面的口徑。** 兩種口徑混用等於沒有預算控制。
8. **「觸發」欄不准省略（2026-08-31 新增）。** 抖動是趨勢訊號：
   >30 分鐘要在報告標出，落在排定 slot 的 −10 至 +90 分窗外要記
   `trigger-jitter-out-of-window`。判定規則見 `modules/m0-clock.md` §1。
   **抖動本身不是失敗，不准因為晚到就改變趟次身分或跳過該做的事。**
9. **有發布就一定要有「已發布」區塊，而且在最前面。** 發完不通報等於沒發完。
10. **能用短報就不要用全報，該用全報就不准用短報。**
   判準只有一個：有沒有發布、有沒有降級、有沒有新缺陷、有沒有模組不是 OK。
